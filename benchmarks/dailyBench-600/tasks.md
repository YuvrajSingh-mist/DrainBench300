# DrainBench: The 28-Day Survival Schedule

### Can a model survive 28 days of an ordinary person's phone habits?

DrainBench measures something no existing mobile-agent benchmark reports: not just whether an LLM agent can complete a task on a real Android phone, but what it actually **costs** to have it do so, in dollars, battery drain, thermal load, and reliability, while running through a schedule shaped like real daily usage rather than an arbitrary task list.

## What this is

Everyday queries across 22 real apps (Gmail, Maps, Chrome, Drive, Photos, YouTube, Telegram, Search, Calculator, Clock, Calendar, Contacts, Notes, Obsidian, Files, Camera, Gallery, Music, Messages, Phone, Settings, and a browser-based Shopping & Delivery category), run live on-device via the accessibility service, not an emulator, not screenshots by default, not vision-model grading. Everything is graded by checking the actual end state a human can verify, because the whole point is measuring real cost, and VLM-based judging would quietly tax exactly the setups (locally-run models) this benchmark cares most about.

## How the difficulty tiers work

- **Easy:** one app, one atomic step. A single tap-level action: star an email, set an alarm, check a status.
- **Medium:** one or two apps, **exactly** three atomic steps: locate/filter something, process it (count, rank, summarize, compare), then act on it. On the runnable 530 subset 199 of 229 stay single-app; 30 genuinely span two apps, so an agent can't assume every medium task lives on one screen.
- **Hard:** two or three apps, **exactly** five atomic steps, genuine reasoning, written as **natural first-person requests rather than terse instructions**. Every hard task is either **DETERMINISTIC** (all its data is on the device, ADB-verified end state) or **ASK USER** (missing one load-bearing fact the agent must actively ask for, resolved by an LLM playing the user, holding only the omitted fact, answering just what's asked). The runnable 530 subset embeds 72 hard tasks into the 28 days (2-3 per day) rather than keeping them in a separate battery, split exactly 36 ASK USER / 36 DETERMINISTIC and interleaved naturally across the days the way the easy and medium tasks are: most days mix both, a handful are all one type, and no run ordering guarantees which.

## The 28-day schedule

Rather than testing each app in an isolated block, the runnable 530 tasks (229 easy, 229 medium, 72 hard) are arranged into a **fixed, one-time-shuffled 28-day schedule**, one simulated day at a time, the way a person actually uses their phone: a quick email check, then a map lookup, then a music skip, then back to email an hour later. Each of the 22 apps hosts its easy/medium tasks on 12-13 of the 28 days and is absent from the ordinary-use schedule the rest of the month, so no app is on screen every single day (the note-taking load is shared 50/50 between Notes and Obsidian, so together they still cover the same days a single note app would). The full corpus is 730 tasks; the **canonical runnable schedule is the deterministic 530-task subset** — see `tasks_530.md` for it as a standalone doc (generated by scripts/export_530_markdown.py from DailyBench_530_v1.json, which is built by scripts/build_530_subset.py) that keeps the same easy/medium/hard and ASK USER/DETERMINISTIC distribution while matching real-world daily density. Every runnable day carries 9-10 distinct apps (min 7, max 11) and ~19 tasks (16-23): about 8 easy, 8 medium, and 2-3 hard, which is how many distinct apps a real person actually touches in a single day (see docs/app-usage-grounding.md). Because every app is fully absent from the ordinary-use schedule for more than half the month, an agent can't camp on any one app's screen and clear everything for it in one pass. The same schedule is reused for every model tested, never re-rolled, so no model gets an easier or harder run by luck of the draw.

The 100 hard tasks are **not** a separate battery run on their own: each one sits inside a day (3-4 per day) alongside that day's easy and medium work, split 50/50 between ASK USER and DETERMINISTIC and mixed naturally day to day (19 of 28 days carry both, 4 days are all ASK USER, 5 are all DETERMINISTIC). Their apps overlap with the day's ordinary-use apps wherever possible, which is how the day's distinct-app count stays at 9-10 even with the hard tasks in the mix.

**App-count rules per tier:** Easy = 1 app. Medium = 1-2 apps (39 of 315 span two). Hard = 2-3 apps, strictly audited.

**Totals (full corpus): 630 easy+medium + 100 hard = 730 total, every task unique, zero cross-tier duplication.** The runnable 530 subset keeps **229 easy + 229 medium + 72 hard (36 ASK USER / 36 DETERMINISTIC)**, every task unique, every task_id traceable to the 730 parent.

## Grading: Manual End-State Check, Weighted by Tier

**Why manual, and why this is fine at this scale.** No VLM/screenshot-based grading anywhere in this benchmark, and that is a deliberate choice. Vision-model calls have real cost, and since the benchmark is meant to run on cloud, local, or on-device models, adding a mandatory VLM judging step would silently tax exactly the setups (locally-run models) the cost-tracking mission cares most about. So grading is a human checking the actual end state after each run, asking whether the note is starred, whether the calendar event exists, and whether the total matches, which is a binary observation, not a judgment call. There's nothing to disagree about, so this doesn't have the rater-inconsistency problem that a rubric-judged bucket would; it only becomes a bottleneck if run volume grows past what one person can eyeball, which isn't the current scale. The one interactive case is an ASK USER task, where the agent's missing-fact question is answered by an LLM playing the user (holding only the omitted fact), and the final end state is still checked by hand the same way.

**Scoring:** points per tier, not just pass/fail.
- **Easy = 1 point.** Single-step tasks; a correct end state is worth its own step.
- **Medium = 3 points.** Every medium task is exactly 3 atomic steps (locate/filter → process → act), so the weight matches the actual work exactly, with no approximation here.
- **Hard = 5 points, exact.** Every hard task is exactly 5 atomic steps, touches 2-3 apps, requires genuine reasoning, and uses varied phrasing rather than a repeated template, and each is tag-audited against its own text. Each hard task is tagged **DETERMINISTIC** or **ASK USER**; an ASK USER task costs an extra simulated-user turn but scores the same flat 5.

**Reporting:** total points earned across the 28-day schedule, out of **1276 max** on the runnable 530 subset (229 easy × 1 + 229 medium × 3 + 72 hard × 5), is the headline score (the full 730 corpus would score out of 1760). Per-tier reliability is reported separately (easy / medium / hard success rates), so the deliberately harder material is never blended into one opaque number.
